# OCR And Categorization Final Implementation Plan

## Purpose

This document is the final implementation plan for adding OCR document intake, AI categorization, pre-posting preview/confirmation, and accounting posting to `ocr/` and the existing Next.js accounting system.

The referenced Markdown files in `docs/` were reviewed as project context only. They do not override the current user request. The active request is to implement OCR plus categorization under `ocr/`, with a workflow that is also suitable for mobile users.

## Current Starting Point

- `ocr/` currently contains only `scanned_docs/`.
- The accounting app already has PostgreSQL migrations, API routing, workflow documents, audit logs, accounting rule mappings, and rule execution logs.
- Existing open checklist items are Phase 3 OCR document intake and Phase 4 AI categorization/approval.
- The app uses Next.js, React, PostgreSQL, Tailwind, shadcn-style components, and responsive navigation.
- The package set does not currently include OCR, PDF conversion, DOCX parsing, image preprocessing, or model SDK dependencies.

## Scope

Implement a complete document-intake workflow:

1. Add two input methods: upload an existing file and take a new photo.
2. Store original files in `ocr/scanned_docs/` during local development.
3. Persist document metadata, processing status, raw OCR text, extracted fields, category results, confidence scores, and pre-posting confirmation state in PostgreSQL.
4. Run OCR through an adapter interface so the implementation can start local and later swap to a cloud or dedicated OCR service.
5. Run categorization and accounting normalization through a model adapter, with Gemma 4 as the target adapter.
6. Show every processed document in a pre-posting review screen before ledger posting.
7. Let users preview and modify extracted fields, category, totals, line items, and suggested journal lines before final submit.
8. Post only after the user saves any corrections and confirms the captured data and posting draft.
9. Preserve source-document traceability for reports, tax, and audit.
10. Make upload, review, confirmation, and posting screens ergonomic on mobile.

## Non-Goals For This Sprint

- Full authentication and role-based access control.
- Production object storage.
- Full tax filing/export implementation.
- External audit system integration.
- Automatic posting without user preview and confirmation.
- Deleting source documents after posting.

## Supported Upload Types

Accept these MIME/file types:

- PDF: `.pdf`, `application/pdf`
- Word: `.doc`, `.docx`
- Images: `.jpg`, `.jpeg`, `.png`

Recommended first limit:

- Maximum file size: 20 MB
- Maximum image dimensions before preprocessing: 6000 x 6000
- Maximum PDF pages for synchronous processing: 5
- Larger PDFs can be uploaded but should process through a queued/background path later.

## Input Methods

Support two first-class document intake paths:

1. Upload file: user selects an existing PDF, DOC, DOCX, JPG, JPEG, or PNG from the device.
2. Take photo: user opens the device camera, captures a receipt/invoice/document image, previews it, then submits it as a document.

Both input methods use the same processing pipeline after storage. Store the source path in `documents.source_channel`:

- `web_upload` for selected files.
- `camera_capture` for photos taken inside the app.

Camera capture requirements:

- Use a mobile-friendly capture input first: `<input type="file" accept="image/*" capture="environment">`.
- Allow retake before submission.
- Show a preview of the captured image before upload.
- Store captured photos as image documents with original filename generated by the app, for example `camera-2026-08-21-153000.jpg`.
- Preserve the original captured image; image cleanup/preprocessing should create derived processing data, not replace the source file.
- If the camera capture attribute is unsupported, fall back to normal image selection.

## Editable Data Before Submit

After OCR and categorization finish, the user must see an editable preview before final confirmation/posting. The first submit only stores the uploaded file or captured photo. The final submit posts accounting data only after the user reviews and confirms the editable draft.

Editable fields:

- Document date.
- Due date.
- Document number.
- Vendor/client name or linked contact.
- Category.
- Currency.
- Subtotal.
- Tax amount.
- Total amount.
- Payment method.
- Line item descriptions.
- Line item quantity, unit price, tax rate, tax amount, and line total.
- Suggested debit/credit accounts.
- Suggested journal line debit and credit amounts.
- User note or correction reason when values are changed.

Editing rules:

- Show OCR/model values as the starting draft, not as locked values.
- Preserve the original OCR text and raw model output unchanged for audit.
- Store user-corrected values in `document_accounting_drafts.normalized_fields`.
- Store changed values in `posting_confirmations.preview_snapshot` when the user confirms.
- Recalculate line totals, subtotal, tax, and total after edits.
- Revalidate category, required fields, totals, and balanced journal lines before allowing final posting.
- Do not post while there are unresolved validation errors.

CREATE TABLE IF NOT EXISTS documents (

## Processing Pipeline

1. User selects a file or takes a photo.
2. API validates size, extension, MIME type, and filename.
3. API calculates SHA-256 hash and prevents duplicate uploads per company.
4. API stores the file under `ocr/scanned_docs/{company_id}/{document_id}-{safe_filename}`.
5. API inserts `documents` row with status `uploaded` then `stored`.
6. Processing service reads the file and sends it to `OcrAdapter`.
7. OCR adapter returns raw text, structured hints, page count, and OCR confidence.
8. Service stores `document_extractions`.
9. Service sends normalized OCR fields to `CategorizationAdapter`.
10. Categorization adapter returns category, confidence, reason, and normalized accounting intent.
11. Service stores `document_categories`.
12. Service creates `document_accounting_drafts`.
13. If confidence is high and required fields are complete, status becomes `needs_review` with a clean preview ready for confirmation.
14. If confidence is low, category is `unknown`, required fields are missing, totals do not reconcile, or journal lines are unbalanced, status becomes `needs_review` with warnings.
15. User previews the captured data: original document, extracted fields, category, totals, and suggested journal entry.
16. User modifies any incorrect captured data, saves the corrected draft, then confirms, rejects, or retries OCR/categorization.
17. Confirmed drafts are posted through the existing accounting rule service.
18. Rule execution logs and audit logs link back to the source document.

## Pre-Posting Review Rules

Every OCR document requires a user preview before posting. Show warning badges and require extra attention when any of these are true:

- Category confidence is below `0.85`.
- OCR confidence is below `0.80`.
- Category is `unknown`.
- Required fields are missing.
- `subtotal + taxAmount` does not equal `totalAmount` within rounding tolerance.
- Suggested journal entry is not balanced.
- Suggested account mapping is missing.
- Document hash is duplicate but metadata differs.
- File type is accepted but extraction is partial.
- Document is a tax, audit, payroll, or bank document.

## Accounting Posting Rules

Map normalized categories to existing accounting rule services:

- `sales_invoice`: create or link an invoice, then use invoice posting rule.
- `vendor_bill`: create or link a vendor bill, then use expense/AP posting rule.
- `receipt_income`: create receipt and post payment receipt rule.
- `receipt_expense`, `petrol`, `entertainment`, `travel`, `office_supplies`, `utilities`, `rent`: use expense document posting rule.
- `inventory_purchase`: create purchase/GRN workflow document first if item lines are present.
- `asset_purchase`: create fixed asset draft or expense document draft depending on threshold.
- `tax_document`, `bank_document`, `unknown`: preview and manual confirmation only; no direct posting shortcut.

Suggested journal entries must always pass existing double-entry validation before posting.

## Adapter Interfaces

OCR adapter:

```ts
export interface OcrResult {
  rawText: string
  fields: Record<string, unknown>
  confidence?: number
  pageCount?: number
  engine: string
}

export interface OcrAdapter {
  extract(input: {
    filePath: string
    mimeType: string
    originalFilename: string
  }): Promise<OcrResult>
}
```

Categorization adapter:

```ts
export interface CategorizationResult {
  category: string
  confidence: number
  reason: string
  normalizedFields: Record<string, unknown>
  suggestedJournalLines: Array<{
    accountId: string
    debit: number
    credit: number
    memo?: string
  }>
  rawOutput: Record<string, unknown>
  modelName: string
  modelVersion?: string
}

export interface CategorizationAdapter {
  categorize(input: {
    rawText: string
    extractedFields: Record<string, unknown>
    companyContext: {
      accounts: Array<{ id: string; code: string; name: string; type: string }>
      ruleMappings: Record<string, unknown>
    }
  }): Promise<CategorizationResult>
}
```

## API Plan

Document API:

- `GET /api/documents`: list documents and statuses.
- `POST /api/documents`: upload selected file or captured photo.
- `GET /api/documents/:id`: fetch metadata, extraction, category, draft, and confirmation status.
- `GET /api/documents/:id/file`: stream or download original file.
- `POST /api/documents/:id/process`: run or retry OCR/categorization.
- `PATCH /api/documents/:id/draft`: save user edits to extracted fields, category, totals, line items, and suggested journal lines.
- `POST /api/documents/:id/confirm`: confirm or edit-and-confirm draft after preview.
- `POST /api/documents/:id/reject`: reject document with reason.
- `POST /api/documents/:id/post`: post confirmed draft to accounting.

Confirmation API:

- `GET /api/posting-confirmations?status=pending`
- `POST /api/posting-confirmations/:id/decision`

## Mobile UI Requirements

Mobile must not be a squeezed desktop table. Use stacked, task-focused screens:

- Upload screen has two clear actions: `Upload File` and `Take Photo`.
- `Upload File` opens the existing file picker.
- `Take Photo` opens the rear camera where supported, then shows a retake/submit preview.
- Both actions use large touch targets and progress/status feedback.
- Document list renders as cards, not a wide table.
- Each card shows filename, status, category, confidence, total, and date.
- Review screen uses tabs or segmented controls:
  - `File`
  - `Fields`
  - `Category`
  - `Journal`
- Editable values use normal form controls before submit; OCR values are suggestions, not locked text.
- Primary action is sticky at the bottom: save edits, confirm, or post depending on state.
- Reject/retry actions sit behind a menu or secondary action row.
- Inputs use mobile-friendly keyboard modes:
  - `inputMode="decimal"` for amounts, quantity, tax rate.
  - `type="date"` for document and due dates.
  - Selects for category/account choices.
- Tables must become horizontal scroll regions or card rows on screens below `md`.
- Preview area must keep a stable aspect ratio and allow pinch/browser zoom where supported.
- Long filenames and extracted text must wrap without overflowing.
- All action buttons should be at least 40 px high.
- Avoid hover-only controls; every action needs a visible touch path.

## Validation And Security

Upload validation:

- Reject unsupported MIME types and extensions.
- Check file signatures where practical.
- Sanitize filenames before storage.
- Store files outside `public/`.
- Never execute or render uploaded HTML/scripts.
- Set download responses with safe `Content-Disposition`.
- Calculate and store SHA-256 hash.
- Enforce file size before processing.
- Accept `source_channel` only when it is `web_upload` or `camera_capture`.

Data validation:

- Required totals must be finite positive numbers.
- Tax rate must be non-negative.
- User edits must be saved to the draft before confirmation.
- Journal draft must be balanced.
- Category must be in the approved taxonomy.
- Posting confirmation must include user, timestamp, and reason for rejection/edit.
